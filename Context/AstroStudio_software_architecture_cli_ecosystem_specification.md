# Astro Studio: Software Architecture & CLI Ecosystem Specification

**Astro Studio** is a decoupled, asynchronous desktop orchestration application built on **GTK** (the native GNOME/Ubuntu standard). Its primary architectural mandate is to act as a pure, zero-processing graphical user interface (GUI) and non-blocking front-end wrapper. 

Rather than implementing internal pixel manipulation or mathematical image processing algorithms, Astro Studio serves exclusively as a visual workspace to load images from the file system, render them on screen, manage multi-format conversions (e.g., opening a JPEG and exporting as a PNG, TIFF, or FITS), and translate user interactions into command-line interface (CLI) instructions executed by external, third-party open-source astronomical and photographic software.

---

## 1. Core Functional Scope & Design Philosophy

* **Zero-Processing GUI Mandate:** Astro Studio performs **no** native image transformations, stacking, or filtering inside the GUI codebase. Every computational task—including format conversion, metadata extraction, calibration, and stretching—is delegated via CLI arguments to specialized external binaries.
* **Multi-Format File I/O:** Users can browse and load standard and astronomical raster formats (e.g., JPEG, PNG, TIFF, RAW, FITS) onto the display canvas and export/save the resulting output into any supported target format via external CLI backends.
* **Non-Blocking Asynchronous Execution:** Because astrophotography and batch image pipelines can take minutes or hours to compute, the GTK event loop remains completely decoupled from subprocess execution.

---

## 2. High-Level Architectural Pattern

Astro Studio follows an **Asynchronous Orchestration Pattern** layered over a modified **Model-View-Controller (MVC)** or **Model-View-ViewModel (MVVM)** architecture:

* **State Manager:** Maintains project state, active file paths, parameter configurations, and target output formats.
* **Command Builder / Templating Engine:** Translates UI parameter widgets and format selections into sanitized argument arrays (`argv`) for CLI invocation.
* **Process Supervisor:** Spawns asynchronous child processes, monitors execution streams (`stdout`/`stderr`), captures exit codes, and triggers UI refreshes upon completion.


## 3. Core Subsystem Breakdown

### A. Presentation Layer (GTK UI Components)
* **Main Window (`GtkApplicationWindow`):** Master layout split into a modular, dockable workspace following GNOME Human Interface Guidelines (HIG).
* **File Browser & Format Exporter:** Native GTK file dialogs (`GtkFileDialog`) and workspace tree views (`GtkColumnView`) allowing users to open images from the hard drive and select target export formats (e.g., `.jpg` to `.png`, `.raw` to 16-bit `.tiff`).
* **Preview Canvas (`GtkImage` / `GtkDrawingArea` with `GdkPixbuf`):** Read-only rendering surface dedicated solely to displaying loaded images and intermediate/final outputs generated by the external CLI tools. It never mutates pixel data.
* **Parameter Inspector:** Dynamic property panels where users configure tool-specific CLI flags (e.g., compression levels, blend weights, demosaicing algorithms, or output dimensions).

### B. Command Builder & Adapter Pattern
To prevent tight coupling with specific external tools, Astro Studio implements an **Adapter Pattern** for CLI integration:
* Each external third-party tool is encapsulated inside an independent adapter module that defines its supported input/output formats and flag syntax.
* The **Command Builder** takes user-configured GUI options and serializes them into safe, sanitized shell argument vectors (`argv`), preventing shell injection vulnerabilities and ensuring robust path handling on Linux.

### C. Process Execution & Concurrency Engine
* **Non-Blocking Concurrency:** Built on top of GLib's event loop (`GMainContext`) using `Gio.Subprocess` from PyGObject (GTK 3.x / Python 3.8 baseline). No subprocess is ever launched synchronously on the GTK main thread.
* **IPC & Stream Monitoring:** Listens asynchronously to the `stdout` and `stderr` pipes of child processes. Regex parsers extract real-time progress indicators to drive progress bars and terminal log drawers in the GTK interface.
* **Process Lifecycle Management:** Provides users with explicit cancellation tokens (`SIGTERM` / `SIGKILL` handlers) to safely abort running CLI jobs.

### D. Temporary Scratch Space Manager
* Manages ephemeral intermediate files under `<XDG_RUNTIME_DIR>/astro-studio/<session>/<job>/` (fallback `/tmp/astro_studio_<pid>/`), passing output paths seamlessly from one CLI command to the next and cleaning up temporary artifacts upon session closure. Original inputs are never modified.

## 4. End-to-End Data Flow Scenario

1. **Image Load:** The user opens `M42_Orion.jpg` (or a raw capture frame) from the hard drive; Astro Studio renders the image onto the GTK Preview Canvas.
2. **Operation & Format Selection:** The user selects an external processing backend (e.g., ImageMagick or RawTherapee) and chooses to convert and save the output as `M42_Orion_processed.png`.
3. **Command Serialization:** The Command Builder generates the concrete CLI instruction:
   ```bash
   magick /path/to/M42_Orion.jpg -unsharp 1.5x1+0.7+0.02 /tmp/astro_studio/M42_Orion_processed.png
   ```
4. **Asynchronous Spawn:** The Process Engine spawns the child process asynchronously, updating the GTK status bar while keeping the UI responsive.
5. **Render & Export:** Upon receiving exit code `0`, Astro Studio loads the newly generated `.png` onto the Preview Canvas and writes it to the user's chosen destination on disk.

---

Every GUI command and toolbar action in `GUI-specifications.md` is an adapter-driven CLI job (collect parameters -> serialize argv -> spawn asynchronously -> read backend artifact from scratch -> render/export). The GUI catalog is the authoritative menu-to-backend map; this document defines the engine that executes it.

A `BackendRegistry` runs at startup: it checks each connector binary with `shutil.which` and queries its version through the same asynchronous `ProcessEngine`. The resulting status feeds the GUI Backends panel and enables/disables `Gio.SimpleAction` menu entries, so unavailable tools never produce failed in-process fallbacks.

Every working image obeys a dual-format invariant managed by `ImageWorkspace`: a 16-bit TIFF in scratch is the only artifact passed to external transformation tools, and an 8-bit PNG regenerated from that TIFF is the only artifact the GUI renders. A transform writes a new TIFF which atomically replaces the old one, then triggers a new TIFF-to-PNG CLI conversion before the canvas is refreshed.

## 5. Supported Open-Source Linux CLI Connectors

The Linux open-source ecosystem provides mature, high-precision imaging and astronomical CLI engines that serve as Astro Studio's execution backends:

### 1. RawTherapee (`rawtherapee-cli`)
* **Overview:** A high-precision RAW image developer powered by a 32-bit floating-point processing engine.
* **CLI Capabilities:** Controlled via `rawtherapee-cli`, supporting custom processing profiles (`.pp3`), batch conversions, bit-depth definitions, and multi-format exports (JPEG, 8/16-bit TIFF, PNG).
* **Example Invocation:**
  ```bash
  rawtherapee-cli -s -p astro_profile.pp3 -o /output/path/ -Y -j92 -c capture.raw
  ```

### 2. Darktable (`darktable-cli`)
* **Overview:** An open-source photography workflow application and non-destructive RAW developer.
* **CLI Capabilities:** Designed for headless batch processing and format export using XMP sidecar files or saved presets (`.dtstyle`).
* **Example Invocation:**
  ```bash
  darktable-cli capture.raw output.png --width 1920 --height 1080 --style "High Contrast"
  ```

### 3. ImageMagick (`magick`)
* **Overview:** The classic command-line Swiss Army knife for raster image manipulation and cross-format conversion.
* **CLI Capabilities:** Built from the ground up for CLI chaining—ideal for instant format conversion (e.g., JPG to PNG/TIFF), resizing, color-space transforms, and spatial filtering.
* **Example Invocation:**
  ```bash
  magick input.jpg -resize 50% -colorspace gray -unsharp 1.5x1+0.7+0.02 output.png
  ```

### 4. GraphicsMagick (`gm`)
* **Overview:** A high-performance, multi-threaded fork of ImageMagick engineered for speed, stability, and low memory overhead.
* **CLI Capabilities:** Invoked via the unified `gm` executable for rapid batch format conversions and geometric transformations on large image sets.
* **Example Invocation:**
  ```bash
  gm mogrify -format png -resize 800x600 *.jpg
  ```

### 5. ExifTool (`exiftool`)
* **Overview:** The industry-standard utility for reading, writing, and editing image metadata (EXIF, IPTC, XMP, FITS headers, camera sensor data).
* **CLI Capabilities:** 100% console-driven; used by Astro Studio to populate the UI metadata inspector (exposure time, ISO, focal length, timestamps) without touching pixel data.
* **Example Invocation:**
  ```bash
  exiftool -T -filename -datetimeoriginal -iso -fNumber *.raw > frame_metadata.txt
  ```

### 6. GIMP (`gimp`)
* **Overview:** Linux's premier open-source raster graphics editor.
* **CLI Capabilities:** Can be invoked in headless batch mode (`-i` / `--no-interface`) to execute **Script-Fu (Scheme)** or **Python-Fu** macros directly from command-line arguments.
* **Example Invocation:**
  ```bash
  gimp -i -b '(batch-resize "*.jpg" 1920 1080)' -b '(gimp-quit 0)'
  ```

### 7. Hugin (`hugin` / `pto_gen`, `nona`, `enblend`)
* **Overview:** An open-source panorama stitcher, image aligner, and HDR assembly suite.
* **CLI Capabilities:** Composed of modular command-line tools (`pto_gen` for project generation, `cpfind` for control-point alignment, `nona` for remapping, and `enblend`/`enfuse` for blending).
* **Example Invocation:**
  ```bash
  pto_gen -o project.pto *.jpg
  cpfind -o project.pto project.pto
  autooptimiser -o project.pto project.pto
  nona -o output project.pto
  ```

### 8. Enblend-Enfuse (`enfuse`)
* **Overview:** A specialized exposure-fusion and focus-stacking engine ideal for combining multi-exposure astrophotography frames (e.g., core vs. outer nebula exposures) without harsh tone-mapping artifacts.
* **CLI Capabilities:** Fully controlled via CLI flags weighting exposure, saturation, and local contrast at the pixel level.
* **Example Invocation:**
  ```bash
  enfuse --exposure-weight=1 --saturation-weight=0.2 --contrast-weight=0.5 -o hdr_result.tiff exposure_*.jpg
  ```

### 9. LibRaw (`dcraw_emu`)
* **Overview:** A foundational open-source library for decoding RAW files from virtually all digital cameras.
* **CLI Capabilities:** Provides `dcraw_emu` to extract linear sensor data with granular control over demosaicing algorithms, white balance, and output bit depth.
* **Example Invocation:**
  ```bash
  dcraw_emu -v -w -H 2 -b 4.0 -T capture.nef
  ```

### 10. PhotoFlow (`photoflow-cli`)
* **Overview:** A non-destructive, layer-based RAW and raster image processor operating in a full 32-bit floating-point color space.
* **CLI Capabilities:** Exposes `photoflow-cli` to execute saved `.pfp` filter pipelines headlessly across batch inputs.
* **Example Invocation:**
  ```bash
  photoflow-cli --input capture.raw --config pipeline.pfp --output result.tiff
  ```
